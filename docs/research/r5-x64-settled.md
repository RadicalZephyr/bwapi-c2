# R5. Settling x64 from existing implementations

Two independent lines of evidence: a layout dump I ran across six targets
(reproducible via [`r5/run-layout-dump.sh`](r5/run-layout-dump.sh)), and the hardcoded
constants three shipping implementations rely on.

**Headline: on Windows the shared-memory layout is byte-identical at 32 and 64 bits, and
`sizeof(GameData)` is 33,017,048 in both. That is not inferred — I computed it, and JBWAPI and
gobwapi both hardcode the same number, gobwapi with a passing test suite. §10.2's two-stage
proof can be deleted.**

**But the matrix turned up one incompatible target the plan does not mention, and it is the one
R7 cares about: 32-bit Linux. There, System V's 4-byte `double` alignment shrinks `BulletData`
from 80 bytes to 76 and shifts every field after `players`, making `sizeof(GameData)` 33,016,644
— 404 bytes short. A 32-bit Linux server and a 64-bit client do not agree.**

---

## 1. The layout matrix

`layout.cpp` reproduces every shared-memory struct with the bodies copied verbatim from
`bwapi/include/BWAPI/Client/*.h`. The single substitution is `BWAPI::UnitCommandType`, whose only
non-static data member is `int tid` (`BWAPI/Type.h:29`) — static members do not affect layout.
That makes the translation unit self-contained, so clang can target Windows without a Windows SDK
and without linking.

| Target | `sizeof(GameData)` | `BulletData` | `offsetof(units)` | `offsetof(xUnitSearch)` |
|---|---|---|---|---|
| `i386-pc-windows-msvc` | **33,017,048** | 80 | 69,656 | 32,962,648 |
| `x86_64-pc-windows-msvc` | **33,017,048** | 80 | 69,656 | 32,962,648 |
| `i386-pc-windows-gnu` (MinGW) | **33,017,048** | 80 | 69,656 | 32,962,648 |
| `x86_64-pc-windows-gnu` | **33,017,048** | 80 | 69,656 | 32,962,648 |
| **`i386-unknown-linux-gnu`** | **33,016,644** | **76** | **69,652** | **32,962,244** |
| `x86_64-unknown-linux-gnu` | **33,017,048** | 80 | 69,656 | 32,962,648 |

`UnitData` (336), `PlayerData` (5,788), `RegionData` (1,068), `ForceData` (32), `Shape` (40),
`UnitCommand` (24), `unitFinder` (8), `Event` (12), `Command` (12), `Position` (8),
`GameInstance` (12) and `GameTable` (96) are identical on **all six** targets.

### Why it holds, and where it breaks

Every leaf field in the shared-memory structs is `int` (173 of them), `bool` (67), `char` (8),
`double` (7) or `unsigned` (1), plus nested PODs of the same and a few plain enums. **There is
not one pointer, `size_t`, `long`, or `#pragma pack` anywhere in `BWAPI/Client/*.h`.** That is
why the layout is bitness-independent in the first place, and it is a property of the header, not
an accident — the one field that could have been a pointer is commented out in `GameTable.h`
(`//time_t lastKeepAliveTime;`, replaced by `unsigned int`).

The single exception is `double` alignment:

- MSVC and MinGW align `double` to 8 bytes in **both** x86 and x64.
- The **i386 System V** ABI aligns `double` to **4**.

`BulletData` is six `int`s then three `double`s then more `int`s and `bool isVisible[9]`, ending
at byte 74. Rounded to align-4 that is 76; to align-8, 80. Multiply by `bullets[100]` and add the
4 bytes of padding that appear before `units` (because `UnitData` inherits align-8 from its own
`double`s, and offset 69,652 is not 8-aligned) and you get the 404-byte total.

**So the divergence is Linux-i386-only.** Windows 32 versus Windows 64 is a non-question.

## 2. Three shipping implementations agree, and none has a bitness branch

| Implementation | Language | `GameData` size | Bitness handling |
|---|---|---|---|
| **JBWAPI** `ClientData.java:70` | Java | `static final int SIZE = 33017048;` | **none** |
| **gobwapi** `internal/shm/constants.go` | Go | `GameDataSize = 33_017_048` | **none** |
| **rsbwapi** `bwapi_wrapper/build.rs` | Rust | generated by bindgen from BWAPI's own headers at build time | **none** |

JBWAPI hardcodes the whole table and every value matches my dump exactly: `BulletData` 80,
`UnitData` 336, `PlayerData` 5,788, `RegionData` 1,068, `ForceData` 32, `Shape` 40,
`UnitCommand` 24, `unitFinder` 8, `Event` 12, `Command` 12, `Position` 8, `GameTable` 96.

gobwapi goes further and **asserts them in a test** (`internal/shm/types_test.go`), fourteen
`unsafe.Sizeof` checks against the same constants. Go on Windows is x64-only, so that is a 64-bit
client asserting a 32-bit server's layout and passing.

**Answering the question as posed: JBWAPI applies no bitness-dependent offset handling whatsoever.
It treats the layout as fixed. Searching `JBWAPI/src/main/java/bwapi/*.java` for `64-bit`,
`is64`, `sun.arch.data.model`, `arch` or `bitness` returns nothing.** Its README states the
support directly: *"Supports both 32-and 64-bit Java (e.g. deeplearning4j requires 64-bit Java…)."*

rsbwapi's README says the same from the other side: *"Windows: You should be fine to just compile
your bot. The resulting **x64 executable** should run fine in all current tournaments/ladders."*

### Caveats and skipped fields: none

`GameData` declares 80 fields. All 80 are exposed by JBWAPI's `ClientData.java` — checked
field-by-field. No skipped fields, no alignment workarounds, no padding fudge. The one
adjustment they made is unrelated to bitness: `ClientData.java` was **generated** from
`clang -Xclang -fdump-record-layouts` (JBWAPI issue #12), which is the same tool this experiment
used and the same conclusion R4 recorded.

## 3. Why BWAPI4J requires 32-bit for retail and 64-bit for OpenBW

**It is a JNI/bridge constraint, not a BWAPI or protocol constraint, and it tells us nothing
about the shared-memory layout.**

BWAPI4J is not a shared-memory client. Searching its tree for `bwapi_shared`,
`CreateFileMapping`, or `MapViewOfFile` returns nothing; it is a `BWAPI4JBridge` C++ library full
of `JNIEXPORT` functions loaded **into the JVM process**. Its README: *"This project consists of
two main parts: the Java project BWAPI4J … and the C++ project BWAPI4JBridge containing C++ code
required for BWAPI4J to interact with BW."*

An in-process native library must match the host process's bitness, and it links BWAPI directly:

- Retail BW ships a 32-bit `BWAPI.dll` → the bridge must be 32-bit → the JVM must be 32-bit.
- OpenBW's build is 64-bit → the bridge is 64-bit → the JVM must be 64-bit.

That is ordinary dynamic linking. JBWAPI, which talks to the same servers over shared memory
instead of linking them, has no such constraint and supports both. **The contrast between the two
Java projects is itself the proof that the bitness limit lives in the linkage model, not in
BWAPI.**

Worth noting for §5.10 and R4: BWAPI4J's README states the batching conclusion in its own words —
*"BWAPI4J minimizes the amount of JNI calls and caches data likely to be queried every frame on
the Java-side using a single large array copy."*

## 4. One real x64 hazard, and it is in the API, not the protocol

§10.2 asks whether the two `clientInfo` pointer↔`int` casts instantiate. They do, and one of them
is broken on 64-bit. `BWAPI/Interface.h`:

```cpp
std::map<int,void*> clientInfo;                     // line 22

void *getClientInfo(int key = 0) const              // line 56 — safe
{ ... return result->second; }

template <typename CT>
CT getClientInfo(int key = 0) const                 // line 70
{ return (CT)(int)this->getClientInfo(key); }       // line 72 — TRUNCATES

template <typename V>
void setClientInfo(const V &clientInfo, int key = 0)
{ this->clientInfo[key] = (void*)clientInfo; }      // widening, safe
```

**You can store a 64-bit pointer and the templated getter will hand back only its low 32 bits.**
It is a template, so it only instantiates when a bot calls it — which is why BWAPI itself has
never tripped over it. Bots do call it: ZZZKBot uses `setClientInfo` 24 times (R2).

This is in the non-virtual `Interface<T>` base, so module mode and client mode are affected
identically, and it is a live upstream bug rather than something a C ABI introduces. **A C ABI
avoids it for free by calling the non-template `getClientInfo(int)` overload**, which returns
`void*` intact — worth writing down as an explicit design note, since exposing per-object user
data is something R2 showed bots want.

## 5. Answers to the questions as asked

**Does JBWAPI apply bitness-dependent offset handling, or treat the layout as fixed?** Fixed,
with no conditional anywhere. `GameData.SIZE = 33017048` is a constant. That is the existence
proof, and my independent layout dump produces the identical number for all four Windows targets.

**Are there documented caveats — fields it skips, alignment it works around?** No. All 80
`GameData` fields are exposed, no padding adjustments, no skipped members. The layout came out of
a clang record-layout dump rather than by hand, which is presumably why.

**BWAPI4J requires 64-bit for OpenBW and 32-bit for retail BW. Why?** Because it is in-process
JNI linking BWAPI directly, so the bridge bitness must match both the JVM and the BWAPI binary.
Nothing to do with BWAPI or the protocol — JBWAPI, a pure client against the same servers,
supports both bitnesses.

## 6. What this does to the plan

**§10.2 does not survive in its current form.** The two-stage proof — layout dumps as a phase-0
gate, cross-bitness interop at the mock-server phase, "final verdict at phase 3" — was sequenced
to answer a question that three shipping implementations answered years ago and that this
experiment answers in one script. Concretely:

- **Delete the phase gate and the phase-3 verdict.** The answer is known: Windows x86 and x64
  layouts are identical, `sizeof(GameData) == 33017048`.
- **Keep the layout dump, demoted to a CI regression check.** `r5/run-layout-dump.sh` runs in
  seconds, needs only clang, and would catch a BWAPI pin bump that changes the layout. That is
  worth having permanently and costs nothing. gobwapi's `types_test.go` is the model.
- **Add the constants as compile-time assertions** in the ABI itself, the way gobwapi does. If a
  pin bump moves `sizeof(GameData)`, the build should fail rather than the bot.

**Add the Linux-i386 hazard to the plan.** It is absent today and it is the one combination that
actually breaks:

| Server | Client | Layout |
|---|---|---|
| Win32 (retail BWAPI) | Win32 or Win64 | agree — 33,017,048 |
| Linux x86-64 (OpenBW) | Linux x86-64 | agree — 33,017,048 |
| **Linux i386** | **Linux x86-64** | **disagree — 33,016,644 vs 33,017,048** |

**This is a direct input to R7.** If OpenBW's Linux build is 64-bit — which BWAPI4J's
"64-bit is required when using OpenBW" implies — the hazard never arises in practice and the
matrix is safe everywhere anyone actually runs. R7 should confirm OpenBW's Linux bitness
explicitly rather than assume it, because the failure mode here is silent: a 4-byte offset shift
that reads plausible garbage rather than crashing.

**Restate non-goal 3 honestly if cross-platform stays out of scope.** The reason to avoid 32-bit
Linux is now a measured number, not a hunch.
