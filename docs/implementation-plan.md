# Implementation plan: executing the five phases

> **Status: provisional.** This document sequences the work; it does not decide it. Every
> design decision lives in [c-abi-plan.md](c-abi-plan.md) and is cited by section. Where a step
> here required a call the plan does not make, the call is stated inline and collected in
> [§7](#7-calls-made-here-not-in-the-plan) so it can be overturned in one place. Update this
> document in place as phases complete; there is no history to preserve.

§12 of the plan gives five phases, one deliverable line and one exit criterion each. That is the
right altitude for a design document and the wrong one for a Monday morning. This document
expands each phase into an ordered sequence of steps sized so that **each step is one commit, or
a short run of commits with one obvious boundary between them**, and each has a check that says
when it is done. Steps within a phase are ordered by dependency; where two steps are independent
it says so.

Three things this document holds to across every phase:

1. **Tests land with or before the code they cover.** The synthetic-fixture substrate (§11) is
   a phase-0 deliverable precisely so that no later wrapper is written without something to run
   it against. A step that adds an export and no test is not finished.
2. **Generated files are checked in and CI proves they are current.** `*.gen.cpp`,
   `bwapi_c2.def`, `api.json` and the three headers are committed (§7); `svnrev.h` is committed
   too, on the BWAPI fork (§10.3). One CI job regenerates and fails on any diff. This makes every generator change a reviewable diff
   in the output, which is the point.
3. **Linux first, Windows for the artifact.** The closure and the whole test suite are
   Linux-native (§11). Development, the fixture suites, the fuzz harness and sanitizers run on
   Linux; Windows CI builds the DLL for x86 and x64, checks the exports against the golden
   `.def`, and builds the consumers. Nothing in a phase's exit criterion depends on a live game
   until phase 3's, which is manual by design.

## 0. Before phase 0: the toolchain matrix

Every step below assumes this and nothing else. Anything not on the list is a new dependency
and needs a sentence in the plan explaining why.

| Windows, manual, one machine with retail Brood War | BWAPI 4.4.0 installed, Chaoslauncher, one map with a natural expansion | The phase-3 exit criterion and the pre-release end-to-end runs (§11) |

**The R5 layout dump runs on Linux.** `run-layout-dump.sh` uses `clang --target=i386-pc-windows-msvc`
and friends with `-fsyntax-only`; nothing links. So both x86 and x64 layout checks are Linux CI
jobs and the Windows job is spared them.

**MSVC toolset.** Upstream pins `v141_xp`. We do not: the DLL targets Windows 7+ and the current
toolset, and `v141_xp` is not a supported CI image. Recorded in §7; the layout is toolset-independent
(R5 covered MSVC and MinGW).

### 0.5 The closure as a CMake target

This is the step everything else links against. Transcribe R6, do not rederive it.

- `CMakeLists.txt` at the root; `cmake/closure.cmake` holding the **explicit** source list —
  `BWAPILIB/UnitCommand.cpp`, every `BWAPILIB/Source/*.cpp` except `Streams.cpp` and
  `BroodwarOutputDevice.cpp`, `Shared/*.cpp`, `BWAPIClient/Source/*.cpp`, BWEM's 14
  `src/*.cpp` — written out file by file, never globbed (§10.1). A new upstream file is a link
  error, which is the intended behaviour.
- Include directories exactly as §10.1 lists them, `include/BWAPI/Client` included, and all of
  them relative to the **inner** roots `third_party/bwapi/bwapi/` and `third_party/bwem/BWEM/`

  `NOMINMAX=1`. Flags: `-fdelayed-template-parsing` on clang, `/MT` on MSVC,
  `-fvisibility=hidden` everywhere non-MSVC. `BWAPI_CUSTOM_COMPILE_FLAGS` as the documented hook.
- Two targets: `bwapi_c2_closure` (an `OBJECT` library — the 44 + 14 TUs) and `BWAPI_C2` (the
  shared library: the closure plus `src/`). Tests link the object library directly so they can
  reach `GameImpl` without going through the C boundary.
- On non-Windows, add R6's `win32stub.cpp` to the closure so `Client.cpp`'s seven imports
  resolve. It is test-only scaffolding and lives at `tests/support/win32stub.cpp`, not `src/`.
- `src/abi.cpp` with exactly one export, `bwapi_abi_version()`, returning `0.0.0`. Enough to
  produce a DLL with a symbol in it.
- `bwapi_c2.def` hand-written with that one symbol; MSVC links with `/DEF`. The generator
  overwrites it in phase 1.
- Commit sequence: *"Add the client-only closure as a CMake object library"*, then *"Add the
  BWAPI_C2 shared library target with a version export"*. **Done.** The closure is 42 BWAPI
  TUs (the 44 R6 compiled minus `Streams.cpp` and `BroodwarOutputDevice.cpp`) plus BWEM's 14
  and, off Windows, the stub. The closure's include directories are `SYSTEM` for consumers, so
  upstream's header warnings do not reach our `-Wall` targets. GCC fails at `CommandTemp.h:34`
  as §10.1 predicts, so configure stops with a message on any non-MSVC compiler but clang; the
  Linux toolchain is clang. `libbwapi_c2.so` exports `bwapi_abi_version` and nothing of BWAPI's.
  `BWAPI_C2_SANITIZERS` (added in 0.11) applies `-fsanitize=` to every target.

**Check:** `cmake -B build && cmake --build build` on Linux produces `libbwapi_c2.so`; on
Windows, `bwapi_c2.dll` for both `-A Win32` and `-A x64`, and `dumpbin /exports` shows
`bwapi_abi_version` undecorated.

### 0.10 The shared fixture builder

The single most important artifact in phase 0, and the one R7 and R11.6 wrote twice.

- `tests/fixture/fixture.h/.cpp`: a `Fixture` class owning a `calloc`'d `GameData`, with
  builder methods — `map(w, h, name)`, `player(id, race, minerals, gas, …)`,
  `unit(id, owner, type, x, y, …)`, `neutral(...)`, `terrain(walkable_rows, buildable_rows,
  heights)`, `event(type, unit, player)` — and a `start()` that sets
  `BWAPI::BWAPIClient.data`, constructs the client `GameImpl`, installs `BroodwarPtr`, and
  calls `onMatchStart()`. Every one of §11's five invariants is encoded in the builder, once:
  the global is set before any `UnitImpl` exists; every unit-index field defaults to `-1`;
  `isPowered` and `isInterruptible` default true for a unit the scenario wants commandable;
  neutrals are delivered through synthesised `UnitDiscover` events so `PlayerImpl::isNeutral()`
  and BWEM both see them; and `neutral(...)` refuses a footprint that partially overlaps an
  existing neutral's (R11.9) unless the call says `stacked` and the footprints are identical.
- A `frame()` method that advances `frameCount`, clears `unitCommands`/`shapes`/`commands`
  counters and re-runs the event pump, so multi-frame tests are possible.
- The test framework: **doctest**, single header, MIT, vendored under `tests/support/`. Plain
  `assert` was what R7 used and it does not report which assertion failed in CI (§7).
- Port R7's harness as `tests/read_write/smoke.cpp` over the builder: client version, frame
  count, map name, the SCV's position, `canMove` true, `canMove` false with `isPowered`
  cleared and `getLastError()` reporting it, and a `move` landing in `data->unitCommands[0]`.
- Port R11.6's fixture as `tests/bwem/analysis.cpp` **with the minerals spaced** (R11.9's
  `--spaced` layout, two free tiles per field): thirty lines of terrain, two areas, one
  chokepoint, two bases with four minerals each, `GetPath` across the wall. Then R11.9's six
  cells as tests: in-place re-`Initialize`, `ResetInstance` then re-`Initialize`, and teardown
  before the fixture is freed all pass on the spaced layout; and one test that asks the builder
  for R11.6's overlapping layout and asserts it is refused, so the invariant is enforced rather
  than remembered.
- Commit sequence: *"Add the shared synthetic-GameData fixture builder"*, *"Port the R7
  read/write harness onto the fixture builder"*, *"Port the R11.6 BWEM analysis fixture"*.
  **Done.** Two findings. `isPowered` cleared fails `canMove` with `Errors::Unit_Busy`, not a
  power-specific code: `Templates.h:416` folds it into the "can be ordered" check. And R11.6's
  start locations at (16,16) and (108,108) were more than three tiles from where BWEM places
  its bases, (22,7) and (104,105), so `FindBasesForStartingLocations()` returned false there and
  R11.6's output recorded `starting=0`; the test puts the start locations on the base tiles and
  asserts `Starting()`. Both suites are clean under valgrind memcheck; this machine lacks clang's
  sanitizer runtimes, so ASan/UBSan runs first in CI.

  three faults report, and the checks are not vacuous - an uninstrumented object or image dropped

## 2. Phase 1 — Generator and static types

**Deliverable (§12):** `draft_spec.py`, the emitters, `check_coverage.py`, `api.json`, the
golden `.def`; `bwapi_c2_types.h` with 848 constants, 185 accessors and the bulk tables;
`Player` fully generated as the proving ground.

**Exit (§12):** ~500 type assertions green with no game; `Player` round-trips spec → header →
`.def` → `api.json` → a compiling Python `ctypes` and C# P/Invoke layer; the coverage audit
reports zero unaccounted declarations across the audited-headers list.

The generator is the deliverable of this phase and the wrappers are its output (§9). The
sequence therefore builds the pipeline end to end on the smallest interface before widening
it, and the boundary implementation in `abi.cpp` before the first generated function that
needs it.

### 1.1 The runtime boundary in `abi.cpp`

Every generated function begins with the same prologue, so it exists before any is generated.

- The sticky error channel: `bwapi_last_error`, `bwapi_last_error_message`,
  `bwapi_clear_last_error`; an internal `latch(code, msg)` that sets only when the current code
  is `NONE` and invokes the error callback at that moment (§4).
- `bwapi_set_log_callback`, `bwapi_set_error_callback`, each with `void* user`.
- Thread affinity: the thread id is recorded in `bwapi_client_connect`; an internal
  `on_abi_thread()` compare; `BWAPI_ERR_WRONG_THREAD` latched on mismatch.
- The `noexcept` boundary as a template: `guard<Neutral>(fn)` wrapping `try { … } catch
  (const std::exception&) { latch(…, what()) } catch (...) { latch(…) }` and returning the
  neutral value. `BWAPI_ERR_BWEM` for a `BWEM::Exception`, distinguished by `dynamic_cast`.
- The thread-local re-entrancy depth counter with `enter/leave` helpers (§5.4). The guard on

### 1.2 The spec format, written down before the first spec file

- `docs/spec-format.md`: the YAML entry schema. Fields: `cpp` (must resolve to exactly one
  declaration; overloads spelled with parameter types), `c`, `self` (`unit | player | force |
  region | bwem_area | bwem_choke | bwem_base | bwem_neutral | none`), `params` (name, type),
  `returns` (`int32 | bool32 | double | type | position | handle:<kind> | string_out |
  id_array | void`), `body` (opaque C++, still fully typed), `skip` (a string naming the rule),
  `reentrant` (`allowed | forbidden`), `legit_none` (true for the §6.2 list), `doc`, `guides`
  (a list of site paths under `how-to/` or `tutorials/`, optional), `since` (an ABI version,
  optional before 1.0 and required after).
- **`doc` is reference-shaped by rule** (§16.1): what it does, parameters, return, neutral
  value, when it latches. No guidance, no examples; those are pages under `guides`. The spec
  format document says so, and a review that finds a "you should" in a `doc:` moves it.
- The neutral value per return kind, stated once here: `0`, `0`, `0.0`, the type's `Unknown`
  or `None` id, the packed `None` of the function's own scale, `BWAPI_NONE`, `0` written and
  `0` returned, `0`, nothing.
- How a `string_out` and an `id_array` entry expand into `(buf, buf_len)` and `(out, cap)`
  parameter pairs, so the spec never spells them.
- Commit: *"Document the spec format"*.

### 1.3 `draft_spec.py`

- Input: a header path and a class name. Runs `clang++ -Xclang -ast-dump=json -Xclang
  -ast-dump-filter=<class> -fsyntax-only` with the closure's include flags, walks the JSON for
  `CXXMethodDecl` under the class, and emits one YAML entry per method with `cpp`, a
  snake_cased `c` under the §4 naming rule, a guessed `self`, and a guessed `returns` from the
  qualified return type. Everything else is left for the human.
- Output goes to `tools/abi/draft/<class>.yaml`, which is gitignored. Drafts are never the
  source of truth; the human copies entries into `tools/abi/spec/<file>.yaml` and edits.
- Include flags come from a single `tools/abi/clang_flags.py` shared with the coverage audit
  so they cannot drift.
- Commit: *"Add draft_spec.py: clang AST dump to draft YAML"*.

### 3.4 The C example bot

This is the exit criterion and the reason the phase exists, so it gets its own step and its own

  -std=c99 -pedantic -Werror` against the `.so`. A C++ compiler is not on the path for that CI

- A smoke run in CI: the bot started with no server exits after `N` failed connects with a

### 3.5 The live run — the manual protocol

## 5. Phase 4 — Consumers → 1.0

**Deliverable (§12):** Python and C# raw layers from `api.json`; the Rust proof-of-concept;
Python and C# example bots; idiomatic wrappers spun out.

**Exit (§12):** both example bots play a game; `bwapi_abi_version()` returns 1.0 and the
append-only promise takes effect.

The raw layers exist from phase 1 as "compiles". This phase makes them *tested*, which needs
the real DLL to be driven from a foreign process in CI without a game. That is what §11's
transport fake is for, so it comes first.

### 4.1 The transport fake

- `tests/transport_fake/`: a ~150-line Windows program that creates the
  `Local\bwapi_shared_memory_game_list` table with one entry, maps
  `Local\bwapi_shared_memory_<pid>` at 33,017,048 bytes, fills it from a fixture (the builder
  from phase 0, so scenarios are shared), creates `\\.\pipe\bwapi_pipe_<pid>`, answers the
  two-byte handshake, and on each frame-end byte from the client increments `frameCount`,
  echoes back, and records the `unitCommands[]` it received to stdout as JSON. No game
  semantics.
- A Linux variant is **not** written; the transport is the one Windows-only piece and this
  test runs in the windows job. (Appendix B's POSIX transport would change that; parked.)
- Test: the C example bot against the fake, in CI, for 50 frames; the recorded commands
  contain a `Gather` from the SCV. This is the first time the real DLL, the real transport and
  a real consumer meet in CI.
- Commit: *"Add the transport fake and run the C example bot against it"*.

### 4.2 Python raw layer, tested

- Finish `bindings/python/gen.py`: struct layouts and flag bits from `api.json`; `numpy`-free
  (a raw layer has no dependencies) but with `ctypes` arrays sized for the retry idiom; a
  `load(path)` that tolerates `bwapi_c2.dll`/`libbwapi_c2.so`.
- `bindings/python/tests/`: `pytest` against the transport fake — connect, 20 frames, snapshot
  decode, packed-position decode, a command round-trip seen in the fake's output, the latch
  read once per frame, the error callback raising a Python exception from a bad handle.
- `examples/python-example-bot/`: the C bot in Python over the raw layer.
- Commits: one for the generator, one for the tests, one for the bot.

### 4.3 C# raw layer, tested

- Same shape: finish the generator (structs with `[StructLayout(Sequential)]`, `[Flags]`
  constants for the snapshot bits), an xUnit project driving the transport fake, and
  `examples/csharp-example-bot/`.
- Commits mirror 4.2.

### 4.4 Rust proof-of-concept

- `bindings/rust/bwapi-c2-sys/`: `build.rs`-free; `src/lib.rs` generated from `api.json` by
  `bindings/rust/gen.py`. As a cross-check, run `bindgen` over `bwapi_c2.h` in CI and diff the
  function signatures it produces against ours — two independent readings of the same ABI must
  agree, and disagreement is a generator bug in one of them.
- A `cargo test` that loads the DLL and runs the version and constant checks; no bot.
- Commit: *"Add bwapi-c2-sys generated from api.json with a bindgen cross-check"*.

### 4.5 The live runs and the ergonomics window

- Run `docs/live-run.md` for the Python and C# bots. Commit the tables.
- **Then stop and change things.** The plan says the ABI is 0.x precisely so that this is the
  moment consumer feedback alters signatures (§4). Budget a bounded window — one sprint's worth
  of changes, each a normal commit with a regen diff — and collect them in `docs/pre-1.0-changes.md`
  so the reasoning survives. Candidates the plan already anticipates: buffer idioms that turned
  out awkward in `ctypes`, flag bits the snapshots are missing, a counter that should exist.
- Nothing in the window may violate §4; if a change wants to, it is a plan revision first.

### 4.6 Release 1.0

## 6. Standing procedures that outlive the phases

- **Pin bump**: §10.3's steps, kept in `docs/pins.md` beside the current pins. The fork moves
  first (rebase `bwapi-c2-pin`, regenerate `svnrev.h` at the upstream commit, push), the
  submodule second. Every step after that is a CI job or a script in this tree by the end of
  phase 1, so a bump is running them in order.
- **Adding an export after 1.0**: a spec entry, a regen, a test, an `api.json` diff that only
  adds. The regen check refuses a changed signature by way of a golden-`.def` diff that shows a
  removal; make that a named CI step, `abi_append_only`, from the 1.0 commit on.
- **The coverage audit** runs at pin bumps and on request, never on the merge path (§9).
- **The site deploys on every push to the default branch** and only from there. A documentation
  fix is a normal commit; there is nothing to publish by hand. External links are checked weekly.
- **Adding a page** means deciding its Diátaxis section first. If it wants to be in two, it is
  two pages.
